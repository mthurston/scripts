# EF Core → Dapper Migration

This directory contains two complete ASP.NET Core 8 Web API solutions implementing the same application — a GitLab issues knowledge base — using different data access strategies.

| Solution | Directory | Strategy |
|----------|-----------|----------|
| **Before** | [`knowledge-base-ef/`](./knowledge-base-ef) | Entity Framework Core 8 |
| **After** | [`knowledge-base-dapper/`](./knowledge-base-dapper) | Dapper + raw SQL |

Reading them side-by-side shows exactly what changes — and what stays the same — when migrating from a full ORM to a micro-ORM.

---

## Why Migrate from EF Core to Dapper?

EF Core is a strong default for most applications. Reasons to migrate toward Dapper typically fall into a few categories:

**Performance at scale.** EF Core generates SQL that is usually good, but not always optimal. Complex queries with multiple `Include()` chains can produce large result sets or multiple round-trips. Dapper lets you write the exact SQL you want, including query hints, index hints, and CTEs that EF cannot express.

**SQL transparency.** In EF Core, the SQL is generated and mostly hidden. When a query behaves unexpectedly you have to intercept it at runtime (logging, SQL profiler) to see what was sent. With Dapper, the SQL is the source of truth — it lives directly in the codebase as a readable string constant.

**Stored procedure and advanced SQL compatibility.** Some teams inherit a SQL Server environment built around stored procedures, `MERGE` statements, `OUTPUT` clauses, or recursive CTEs. EF Core can call these but cannot express them natively via LINQ. Dapper treats them as first-class citizens.

**Removing the migration toolchain dependency.** EF migrations require the `dotnet ef` CLI tool, a design-time `DbContext`, and careful coordination between code and database state. Teams that manage schema separately (DBAs, dedicated schema repos, Flyway/Liquibase) often prefer Dapper's "just run the SQL script" approach.

**Simpler mental model.** Dapper has no change tracker, no identity map, no lazy loading, no proxy generation. You write a query, you get objects back. For read-heavy APIs this simplicity reduces cognitive overhead and eliminates a class of bugs caused by accidental lazy loading or unexpected entity state mutations.

## What Changes in the Migration

### 1. NuGet Packages (`KnowledgeBase.Data.csproj`)

| EF Core | Dapper |
|---------|--------|
| `Microsoft.EntityFrameworkCore.SqlServer` | `Dapper` |
| `Microsoft.EntityFrameworkCore.Tools` | `Microsoft.Data.SqlClient` |

The Core and Api projects require no package changes.

---

### 2. Schema Management

EF Core manages the database schema through **migrations** — C# classes generated by `dotnet ef migrations add` that describe incremental schema changes. The schema is applied by `dotnet ef database update` or programmatically via `context.Database.Migrate()`.

Dapper has no schema management. Schema is expressed as **plain SQL scripts** maintained by hand:

```
knowledge-base-dapper/src/KnowledgeBase.Data/Schema/001_InitialSchema.sql
```

The script is idempotent (`IF NOT EXISTS` guards on each `CREATE TABLE`) and applied manually:

```bash
sqlcmd -S "(localdb)\mssqllocaldb" -d KnowledgeBaseDb \
       -i src/KnowledgeBase.Data/Schema/001_InitialSchema.sql
```

**Migration tip:** When migrating an existing EF Core application, generate the schema script from your last migration rather than hand-writing it:

```bash
dotnet ef migrations script --idempotent \
  --project src/KnowledgeBase.Data \
  --startup-project src/KnowledgeBase.Api \
  --output schema.sql
```

This produces an idempotent SQL script you can use as the starting point for your Dapper schema directory.

### 3. `DbContext` → `IDbConnectionFactory`

**EF Core** — one `DbContext` per request, registered with `AddDbContext<>`:

```csharp
// Program.cs (EF Core)
builder.Services.AddDbContext<KnowledgeBaseDbContext>(opts =>
    opts.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
```

```csharp
// KnowledgeBaseDbContext.cs
public class KnowledgeBaseDbContext : DbContext
{
    public DbSet<Issue> Issues => Set<Issue>();
    public DbSet<Comment> Comments => Set<Comment>();
    // ...
    protected override void OnModelCreating(ModelBuilder modelBuilder)
        => modelBuilder.ApplyConfigurationsFromAssembly(typeof(KnowledgeBaseDbContext).Assembly);
}
```

**Dapper** — a singleton factory that opens a new `IDbConnection` per repository call:

```csharp
// Program.cs (Dapper)
builder.Services.AddSingleton<IDbConnectionFactory, SqlConnectionFactory>();
```

```csharp
// SqlConnectionFactory.cs
public class SqlConnectionFactory : IDbConnectionFactory
{
    private readonly string _connectionString;
    public SqlConnectionFactory(IConfiguration config)
        => _connectionString = config.GetConnectionString("Default")!;

    public IDbConnection CreateConnection() => new SqlConnection(_connectionString);
}
```

The entire `Context/` and `Configurations/` folders are deleted. No `DbSet<>` properties, no `IEntityTypeConfiguration<T>` classes, no model builder.

---

### 4. Entity Configurations → SQL Schema

Each `IEntityTypeConfiguration<T>` class in EF Core expresses constraints that become DDL in Dapper's SQL script. The relationship is direct:

| EF Core configuration | Equivalent in `001_InitialSchema.sql` |
|-----------------------|---------------------------------------|
| `builder.HasIndex(u => u.GitLabUserId).IsUnique()` | `CONSTRAINT UQ_Users_GitLabUserId UNIQUE (GitLabUserId)` |
| `builder.Property(i => i.Title).HasMaxLength(500)` | `Title NVARCHAR(500) NOT NULL` |
| `builder.HasOne(c => c.ParentComment).WithMany(c => c.Replies).OnDelete(DeleteBehavior.Restrict)` | `ParentCommentId INT NULL REFERENCES Comments(Id)` (no `ON DELETE CASCADE`) |
| `builder.HasKey(il => new { il.IssueId, il.LabelId })` | `CONSTRAINT PK_IssueLabels PRIMARY KEY (IssueId, LabelId)` |

The self-referencing `Comment` FK deserves special attention. EF Core's `OnDelete(DeleteBehavior.Restrict)` prevents cascade delete loops. In the SQL schema this is expressed by simply omitting `ON DELETE CASCADE` from the self-referencing FK — SQL Server's default behaviour is `NO ACTION`, which is functionally equivalent.

### 5. Repositories — LINQ → Raw SQL

This is the largest change. Every repository method that uses LINQ and navigation properties is replaced by a SQL string + Dapper call.

#### Simple list query

**EF Core:**
```csharp
return await _context.Users
    .Select(u => new UserDto { Id = u.Id, Name = u.Name, Username = u.Username })
    .ToListAsync(ct);
```

**Dapper:**
```csharp
using var connection = _connectionFactory.CreateConnection();
var rows = await connection.QueryAsync<dynamic>("SELECT Id, Name, Username FROM Users ORDER BY Name");
return rows.Select(r => new UserDto { Id = (int)r.Id, Name = (string)r.Name, Username = (string)r.Username });
```

#### Filtered query with eager-loaded related data

**EF Core** — LINQ with `Include()`, filter via `.Where()`:
```csharp
var query = _context.Issues
    .Include(i => i.Author)
    .Include(i => i.IssueLabels).ThenInclude(il => il.Label)
    .AsQueryable();

if (!string.IsNullOrWhiteSpace(stateFilter))
    query = query.Where(i => i.State == stateFilter);
// ...
return await query.Select(i => new IssueSummaryDto { ... }).ToListAsync(ct);
```

**Dapper** — one SQL string with optional filter parameters, a LEFT JOIN for labels, and a dictionary to collapse the one-row-per-label fan-out:
```csharp
// The query LEFT JOINs labels, returning one row per label per issue
var rows = await connection.QueryAsync<dynamic>(IssueQueries.GetAll,
    new { State = stateFilter, Author = authorFilter, Label = labelFilter });

var issueLookup = new Dictionary<int, IssueSummaryDto>();
foreach (var r in rows)
{
    if (!issueLookup.TryGetValue((int)r.Id, out var dto))
    {
        dto = new IssueSummaryDto { ... };
        issueLookup[(int)r.Id] = dto;
    }
    if (r.LabelId is not null)
        dto.Labels.Add(new LabelDto { ... });
}
return issueLookup.Values;
```

#### Upsert

**EF Core** — `FirstOrDefaultAsync` + entity state tracking:
```csharp
var user = await _context.Users.FirstOrDefaultAsync(u => u.GitLabUserId == gitLabUserId, ct);
if (user is null) { user = new User { ... }; _context.Users.Add(user); }
else              { user.Name = name; user.Username = username; }
await _context.SaveChangesAsync(ct);
```

**Dapper** — single `MERGE` statement, no SELECT round-trip, `OUTPUT` returns the persisted Id:
```sql
MERGE Users AS target
USING (SELECT @GitLabUserId, @Name, @Username) AS source
    ON target.GitLabUserId = source.GitLabUserId
WHEN MATCHED     THEN UPDATE SET Name = source.Name, Username = source.Username
WHEN NOT MATCHED THEN INSERT (GitLabUserId, Name, Username)
                      VALUES (source.GitLabUserId, source.Name, source.Username)
OUTPUT INSERTED.Id, INSERTED.GitLabUserId, INSERTED.Name, INSERTED.Username;
```

### 6. Threaded Comments — The Most Complex Migration Step

The self-referencing `Comment` entity drives the largest technical divergence. Both approaches ultimately use the same O(n) dictionary tree-builder in C#, but they differ significantly in how they retrieve the data.

#### EF Core approach

EF Core loads comments flat (it does not auto-recurse `Replies`) and builds the tree in C#:

```csharp
// Load all comments for the issue in one query
var allComments = await _context.Comments
    .Include(c => c.Author)
    .Where(c => c.IssueId == issueId)
    .OrderBy(c => c.CreatedAt)
    .ToListAsync(ct);

// Build tree
var lookup = allComments.ToDictionary(c => c.Id, MapToDto);
var roots = new List<CommentDto>();
foreach (var dto in lookup.Values)
    if (dto.ParentCommentId is null) roots.Add(dto);
    else lookup[dto.ParentCommentId.Value].Replies.Add(dto);
```

#### Dapper approach

Dapper uses a **recursive CTE** to express the full traversal in SQL, then applies the identical C# tree builder:

```sql
WITH CommentTree AS (
    -- Anchor: root-level comments
    SELECT c.*, 0 AS Depth
    FROM Comments c
    WHERE c.IssueId = @IssueId AND c.ParentCommentId IS NULL

    UNION ALL

    -- Recursive: attach each child to its parent
    SELECT c.*, ct.Depth + 1
    FROM Comments c
    INNER JOIN CommentTree ct ON c.ParentCommentId = ct.Id
)
SELECT ct.*, u.Id AS AuthorId, u.Name AS AuthorName, u.Username AS AuthorUsername
FROM CommentTree ct
INNER JOIN Users u ON u.Id = ct.AuthorId
ORDER BY Depth, CreatedAt
OPTION (MAXRECURSION 100);
```

```csharp
var rows = await connection.QueryAsync<dynamic>(CommentQueries.GetThreadedByIssueId, new { IssueId = issueId });
var flatList = rows.Select(MapToDto).ToList();
return BuildCommentTree(flatList);   // same dictionary algorithm as EF version
```

Both arrive at the same result. The CTE is more explicit about the traversal strategy and expresses maximum recursion depth as a tunable SQL-level constraint (`OPTION (MAXRECURSION 100)`).

### 7. `Program.cs` DI Registration

The only change to `Program.cs` is swapping the data access registration:

```csharp
// EF Core
builder.Services.AddDbContext<KnowledgeBaseDbContext>(opts =>
    opts.UseSqlServer(builder.Configuration.GetConnectionString("Default")));

// Dapper (replace the above with)
builder.Services.AddSingleton<IDbConnectionFactory, SqlConnectionFactory>();
```

All other registrations (repositories, services, controllers, Swagger, middleware) are identical.

---

### 8. What Stays the Same

The migration touches only the `KnowledgeBase.Data` project and two lines of `Program.cs`. Everything else is unchanged:

| Layer | Unchanged? |
|-------|-----------|
| `KnowledgeBase.Core/Domain/` | Yes — domain models are persistence-ignorant |
| `KnowledgeBase.Core/DTOs/` | Yes |
| `KnowledgeBase.Core/Interfaces/` | Yes — repository interfaces define the contract, not the implementation |
| `KnowledgeBase.Core/Models/GitLab/` | Yes |
| `KnowledgeBase.Api/Controllers/` | Yes — controllers depend only on interfaces |
| `KnowledgeBase.Api/Middleware/` | Yes |
| `KnowledgeBase.Data/Services/GitLabService.cs` | Yes — HTTP client logic is unaffected |

This is a key benefit of the architecture: by keeping repositories behind interfaces defined in `Core`, the entire data access layer can be replaced without touching the API surface, controllers, or domain logic.

## Migration Checklist

When applying this pattern to your own EF Core application:

- [ ] Generate an idempotent SQL schema script from your latest migration: `dotnet ef migrations script --idempotent`
- [ ] Add `Dapper` and `Microsoft.Data.SqlClient` to your data project; remove `Microsoft.EntityFrameworkCore.*`
- [ ] Implement `IDbConnectionFactory` / `SqlConnectionFactory`
- [ ] Delete `DbContext`, `Migrations/`, and all `IEntityTypeConfiguration<T>` classes
- [ ] Replace each repository's LINQ body with a SQL query constant + Dapper call
- [ ] Replace `FirstOrDefaultAsync` + EF upsert pattern with `MERGE` statements
- [ ] For self-referencing hierarchies, replace EF flat-load with a recursive CTE (the C# tree-builder is identical)
- [ ] In `Program.cs`, swap `AddDbContext<>` for `AddSingleton<IDbConnectionFactory>`
- [ ] Remove `context.Database.Migrate()` from startup; apply schema manually or via a migration runner
- [ ] Run integration tests against both implementations to verify equivalent behaviour before decommissioning EF Core
